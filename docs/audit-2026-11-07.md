# Audit keamanan, fungsi, dan performa HC-Dashboard

Tanggal: 7 November 2026, WITA. Pemeriksaan dan percobaan aktif dilakukan secara lokal dengan akun sintetis. Tidak ada percobaan terhadap produksi, brute force massal, DoS, pengiriman email sungguhan, atau penghapusan data aplikasi.

## Lingkungan dan cakupan

- Kondisi Git awal bersih. Seeder tidak diubah atau dijalankan pada database aplikasi.
- PHP 8.3.30, Laravel 13.33.0, PHPUnit 12.5.35, PhpSpreadsheet 5.10.0, Node 24.15.0, Vite 8.3.5, Alpine 3.17.4, ApexCharts 8.4.1. Versi dikonfirmasi melalui paket terpasang dan lockfile.
- Database aplikasi MySQL diperiksa hanya melalui metadata/skema. Pengujian fitur menggunakan SQLite `:memory:`, mail array/fake, serta penyimpanan palsu saat diperlukan.
- Terdapat 217 route aplikasi: movement 51; WLA/workforce 38; organisasi 31; Fit & Proper 27; pegawai HC 21; Performance & Talent 17; pengguna 8; autentikasi/portal/lainnya 24.
- Ditinjau: route, middleware, login/session/reset password, izin role/workspace, policy, FormRequest, relasi/model/migration, Blade/JavaScript, impor staging, persetujuan, ekspor, dan penyimpanan file. Log diperiksa tanpa menampilkan kredensial, token, atau data pribadi.

## Temuan terverifikasi dan perbaikan

### 1. Critical, bersyarat: eskalasi melalui pengelolaan role yang didelegasikan

Prasyarat: Super Admin memberikan izin `users.manage-roles` kepada role lain melalui matriks izin yang didukung aplikasi. Tidak memerlukan akses database langsung.

Bukti lokal: request `PATCH` ke route `konfigurasi-user.role` dengan role tujuan `Super Admin` sebelumnya berhasil untuk akun sendiri maupun akun lain. Pemeriksaan lama hanya melindungi target yang sudah menjadi Super Admin. Akun hasil promosi memperoleh izin khusus Super Admin, termasuk pengelolaan akses.

Perbaikan: `UserManagementController::updateRole` menolak tujuan Super Admin apabila pelaku bukan Super Admin. Regresi mencakup empat role non-super, promosi diri/akun lain, delegasi role biasa yang tetap sah, dan promosi oleh Super Admin yang tetap berhasil.

### 2. Critical, bersyarat: perubahan email pemulihan Super Admin melalui pegawai

Prasyarat: akun Super Admin terhubung ke Employee dan pelaku memperoleh delegasi `employees.update` atau `employees.import`.

Bukti lokal: request edit pegawai dan proses batch yang sudah disetujui dapat mengganti email akun terhubung dari `protected@example.test` ke alamat uji lain. Perlindungan target Super Admin pada pengelolaan pengguna tidak diterapkan melalui jalur sinkronisasi pegawai. Pengambilalihan berikutnya melalui email pemulihan merupakan dampak dari kemampuan mengubah email; tidak ada pengambilalihan akun nyata atau pengiriman email sungguhan.

Perbaikan: `StaffUserProvisioningService::synchronizeLinkedUser` menerima pelaku, mempertahankan role, dan menolak perubahan identitas akun Super Admin oleh non-super. Controller edit dan proses impor meneruskan pelaku. Transaksi membatalkan perubahan pegawai serta seluruh batch jika ditolak, termasuk baris yang sudah diproses lebih dahulu dalam transaksi yang sama. Perubahan non-identitas dan perubahan sah oleh Super Admin tetap berhasil.

### 3. High, bersyarat: Host poisoning pada tautan reset password

Prasyarat: web server/proxy menerima Host yang bukan domain resmi aplikasi.

Bukti lokal: permintaan reset melalui host `attacker.example.test` menghasilkan notifikasi palsu dengan URL reset pada host tersebut, walaupun `APP_URL` menunjuk host resmi. Token tidak dicetak dan notifikasi tidak dikirim.

Perbaikan: callback `ResetPassword::createUrlUsing` di `AppServiceProvider` membentuk URL dari `app.url` dan named route relatif. Regresi memeriksa host, HTTPS, parameter email, serta pemasangan pada subdirektori. `APP_URL` yang benar tetap merupakan prasyarat penerapan.

### 4. Medium: sinkronisasi pegawai mengubah role akun secara diam-diam

Bukti lokal: edit identitas pegawai mengubah role akun terhubung, termasuk Super Admin, menjadi Staff. Ini juga dapat menghilangkan administrator terakhir melalui jalur di luar pengelolaan akun.

Perbaikan: sinkronisasi hanya mengubah identitas; role yang sudah ditetapkan tetap dipertahankan. Regresi mencakup seluruh lima role.

### 5. Medium: struktur XLSX rusak menghasilkan HTTP 500

Prasyarat: akun memiliki izin impor pegawai. Dampaknya adalah kegagalan request impor dan batch yang tidak dapat ditinjau dengan benar.

Bukti lokal: unggah XLSX tanpa `sheetData` atau dengan XML rusak menghasilkan `foreach(null)`/warning parser dan HTTP 500.

Perbaikan: struktur XML diperiksa secara eksplisit, error libxml ditangani dan status sebelumnya dipulihkan. File menjadi batch `INVALID` dengan pesan yang dapat ditinjau; tidak ada Employee yang disimpan.

Penguatan tambahan, tanpa menjalankan DoS: maksimal 10.000 baris pegawai, 20 MiB setiap XML setelah dekompresi, 50 MiB total arsip setelah dekompresi, dan 1.000 entri. Ukuran diperiksa sebelum XML didekompresi; DTD/entity declaration ditolak. Batas dapat disesuaikan di `config/workforce.php`. Pengujian menggunakan batas kecil serta fixture aman, termasuk penerimaan tepat pada batas baris.

Tinjauan lanjutan membuktikan regex ASCII saja dapat dilewati oleh deklarasi DTD dalam UTF-16LE/BE. Pemeriksaan doctype DOM setelah parsing menutup bypass encoding ini. Dua regresi menggunakan deklarasi internal kecil; tidak ada akses eksternal, pengambilan file, atau eksploitasi XXE yang dilakukan/diklaim.

### 6. Medium: penggantian placeholder DOCX dapat berulang tanpa akhir

Prasyarat: terdapat rekaman mutasi dengan token pada nama dan akun berizin menjalankan pencetakan. Dampaknya dapat menahan request cetak tersebut.

Bukti deterministik dari kode: loop penggantian `[NAMA]` mencari ulang teks yang baru disisipkan. Nilai nama yang memuat token tersebut memasukkannya kembali pada setiap iterasi. Request yang menggantung sengaja tidak dijalankan sebelum perbaikan.

Perbaikan: cari posisi token pada teks asli, lalu ganti dari kanan ke kiri. Regresi endpoint cetak setelah perbaikan memastikan `Nama [NAMA] <literal>` selesai diekspor, tetap utuh, dan XML ter-escape. Template yang memecah token ke beberapa node tetap didukung.

### 7. Medium: status dan kontrol Fit & Proper tidak konsisten setelah pembaruan

Dua pengujian interaksi awal gagal. Hook pencarian PIC tidak tersedia dan teks jumlah penguji tidak sesuai keadaan penugasan. Tinjauan JavaScript juga menemukan pembaruan struktural melewatkan heading/ringkasan, sehingga status lama dapat tetap tampil.

Perbaikan mengembalikan hook pencarian, menampilkan jumlah penguji yang ditugaskan, dan memperbarui seluruh fragment terkait ketika struktur berubah. Desain dan alur penilaian dipertahankan.

### 8. Medium: ID detail pegawai yang tidak valid menghasilkan HTTP 500

Prasyarat: akun dapat membuka data pegawai pada workspace terkait. Ini merupakan kesalahan penanganan input, bukan bypass autentikasi.

Bukti lokal: ID alfabetis dan angka yang melampaui kapasitas integer PHP memicu `TypeError` pada detail pegawai di kedua workspace. Route kini membatasi ID numerik, dan controller menerima ID sebagai string untuk query terikat. Delapan kasus regresi mencakup format tidak valid serta detail numerik yang tetap berfungsi.

### 9. Medium: regresi offset pada optimasi awal ekspor

Bukti regresi terkendali pada versi optimasi awal: sisipan SAP lebih kecil setelah chunk pertama membuat ekspor berbasis offset menghasilkan 502 baris untuk 501 pegawai awal. Regresi ini ditemukan saat review dan diperbaiki sebelum penyelesaian pekerjaan. Tidak ada request paralel atau perubahan data aplikasi yang dilakukan; perubahan disisipkan pada batas query database uji.

Perbaikan: pembacaan memakai kelanjutan berdasarkan SAP unik (`lazyById(500, 'sap')`), dengan urutan SAP dan chunk 500 tetap dipertahankan. Regresi setelah perbaikan menghasilkan 501 SAP unik. Ini tidak menjanjikan snapshot seluruh ekspor pada satu titik waktu ketika SAP sedang diubah secara bersamaan.

## Performa dan pengukuran

Perubahan terukur pada tingkat kode/query:

- Master Organization memakai lima query agregat untuk lima tingkat organisasi, sebelumnya sepuluh. Jumlah total/aktif dan tingkat kosong diuji melalui request halaman.
- Ekspor pegawai hanya memilih kolom ekspor dan membaca model dalam chunk 500 baris. Tiga eager-loaded relation yang tidak dipakai dihapus. Regresi 501 baris memastikan urutan SAP, kelengkapan batas chunk, dan nilai formula tetap berupa string.
- GSAP dimuat ketika animasi halaman membutuhkannya. Nilai statistik tetap harus tersedia melalui HTML server dan sebelum pemuatan animasi selesai.
- Data Pegawai sebelumnya memuat 20 dialog edit lengkap pada HTML awal, sekitar 829 KB dan 5.298 node DOM dalam fixture. Dialog kini diminta saat dibuka melalui route yang sama dengan izin `employees.update` eksplisit dan respons `private, no-store`. Input lama dan error validasi tetap dirender ketika perlu dibuka kembali, termasuk pegawai di luar filter/pagination saat ini.
- Successor View mempertahankan departemen pertama/pilihan awal yang terlihat. Pohon departemen lain serta profil kandidat yang belum dipilih dimuat saat dibuka melalui fragment dengan policy, validasi ID master aktif, dan `private, no-store`. Seluruh posisi dan profil tetap tersedia; form profil tetap manual.
- Grafik Talent Pool di bawah layar dimuat ketika terlihat. Statistik pegawai tersedia sejak HTML awal; animasi tidak menyembunyikan atau menghitung ulang nilai yang sudah benar sambil menunggu grafik.
- SweetAlert dan CSS dialog dimuat saat digunakan. Semua pemanggilan konfirmasi dipertahankan. Kegagalan pemuatan dicatat dan ditampilkan kepada pengguna, dengan hasil konfirmasi ditolak; tindakan tidak disetujui otomatis.

Build akhir menurunkan JavaScript awal dari 236,54 KB menjadi 90,45 KB (gzip 77,09 KB menjadi 29,67 KB). Kode GSAP/SweetAlert dan CSS dialog tetap tersedia sebagai chunk yang dimuat saat diperlukan. Grafik pegawai memakai entry resmi ApexCharts 8.4.1 untuk core, line, bar, serta keyboard: payload grafik berkurang dari 921,91 KB menjadi 652,94 KB (gzip 270,29 KB menjadi 191,32 KB). Tema dan grafik diperiksa kembali di browser.

Pengukuran memakai Lighthouse 13.6.0 dan Edge 157.0.4341.42, Windows x64, Intel Core i5-12450H, 12 logical CPU, RAM 16 GiB. Server loopback `http://127.0.0.1:8187` memakai PHP 8.3, SQLite terpisah, `APP_DEBUG=false`, serta production build Vite. Ini bukan pengukuran server produksi; stylesheet/aset statis PHP built-in server dikirim tanpa konfigurasi kompresi reverse proxy produksi.

Akun pengukuran adalah Super Admin sintetis. Data sama pada kedua fase: 1.080 pegawai, 216 posisi, 6 departemen, 36 profil Successor manual, 24 kegiatan Fit & Proper, 240 peserta, dan 24 penguji. Baseline diambil setelah perbaikan keamanan/dependensi dan sebelum optimasi render/aset. Kondisi fungsi keamanan berlaku pada kedua fase.

Profil desktop: 1.350 × 940, DPR 1, CPU ×1, RTT 40 ms, throughput 10.240 Kbps. Profil mobile: 412 × 823, DPR 1,75, CPU ×4, RTT 150 ms, throughput 1.638,4 Kbps. Keduanya memakai throttling simulasi Lighthouse. Cache HTTP browser dibersihkan sebelum setiap run; cookie autentikasi dipertahankan, tanpa meneruskan cookie ke domain font. Font Bunny yang sama tetap digunakan, dengan preload font heading pada versi akhir.

Setiap kombinasi halaman/perangkat diukur tiga kali: 36 run baseline dan 36 run akhir. Median dihitung untuk setiap metrik secara terpisah. Seluruh 72 run lolos pemeriksaan path tujuan, runtime, aset aplikasi, serta stylesheet/font Bunny. Probe selama optimasi dipisahkan dari pengukuran akhir.

## Verifikasi

- Suite lengkap pada kode akhir: **751 kasus; 750 lulus; 1 dilewati; 7.873 assertion**. Kasus yang dilewati membutuhkan konkurensi MySQL, sedangkan pengujian memakai SQLite. Hasil tersimpan pada [log pengujian akhir](../storage/logs/audit-final.log).
- Pengujian otorisasi baru: request langsung tanpa hak ditolak; pelaku yang sah tetap berhasil; penolakan impor membatalkan seluruh transaksi.
- Pengujian impor mencakup file rusak, batas arsip/XML/baris, staging/approval/process, duplikasi SAP, serta nilai succession. Pengujian ekspor memeriksa formula sebagai teks dan kelengkapan 501 baris.
- Pemeriksaan WLA/work calendar/work schedule: 164 lulus, 1.284 assertion. Ini tidak membuktikan perilaku lock/deadlock pada MySQL.
- Pint `--dirty --format agent`, validasi Composer, pemeriksaan sintaks empat file JavaScript yang berubah, dan `git diff --check` lulus. Production build akhir berhasil dan merupakan build yang dipakai untuk 36 run akhir.
- Browser Edge memverifikasi dialog edit beserta opsi organisasi, pembatalan konfirmasi, pemuatan grafik saat terlihat, kedua grafik pegawai dan perubahan tema, pembaruan heading/ringkasan Fit & Proper setelah transisi, serta pergantian departemen/kandidat dan input manual nama/SAP Successor. Tidak ada `pageerror` pada alur yang diuji. Data uji Fit & Proper dibersihkan kembali dan seluruh jumlah fixture tetap sama.
- Server serta browser benchmark telah dihentikan. Laporan mentah dan database sintetis dipertahankan; helper sementara yang dapat menulis ulang sumber dihapus. Git awal bersih dan diff seeder tetap kosong.

## Dependensi

Audit awal Composer melaporkan delapan advisory pada lima paket Symfony. Setelah persetujuan pengguna, hanya lima paket diperbarui: `http-foundation`, `http-kernel`, `routing`, dan `yaml` ke 7.4.23; `mime` ke 7.4.22. `composer.json` tidak berubah. Audit Composer setelah pembaruan tidak melaporkan advisory atau paket abandoned; audit npm juga tidak melaporkan advisory. Ini merupakan hasil database advisory saat pemeriksaan, bukan jaminan tidak ada kerentanan lain.

Contoh sumber primer: [advisory HTTP Foundation](https://symfony.com/cve-2026-118514), [URL host injection](https://github.com/symfony/symfony/security/advisories/GHSA-5mx8-mwrp-5693), dan [MIME header injection](https://symfony.com/cve-2026-45070). Kondisi spesifik setiap advisory tidak seluruhnya direproduksi pada aplikasi; temuan dependensi dibedakan dari eksploitasi aplikasi yang terverifikasi di atas.

## Batasan dan masalah terbuka

- **Fit & Proper mobile masih 77/100.** FCP/LCP median sekitar 4,1 detik, sementara TBT dan CLS sudah nol. HTML awal sekitar 270 KB, stylesheet aplikasi sekitar 215 KB, serta rantai font eksternal masih membebani render pada jaringan mobile simulasi. Belum dilakukan pemisahan CSS lebih luas, pagination/perombakan rendering daftar kegiatan, atau pengukuran ulang pada server produksi dengan kompresi. Tidak ada klaim bahwa target halaman ini sudah tercapai.
- Seeder yang ada berisi kredensial akun demo eksplisit, termasuk Super Admin, tanpa guard lingkungan pada seeder tersebut. Seeder tidak diubah sesuai instruksi. Tidak diperiksa apakah kredensial itu masih digunakan oleh akun nyata. Akun hasil seeder di luar pengembangan perlu ditinjau dan kredensialnya diganti oleh pengelola.
- Belum dilakukan uji konkurensi paralel MySQL, SMTP nyata, beban maksimum, atau pemeriksaan konfigurasi server produksi/TLS/proxy/scheduler. Lingkungan lokal menggunakan debug; konfigurasi produksi tidak disimpulkan dari keadaan lokal.
- Lighthouse mengukur enam halaman indeks dengan role Super Admin. Role lain dan detail penilaian Fit & Proper belum diukur dengan Lighthouse. Interaksi tertentu diuji di browser dengan data sintetis, bukan seluruh kombinasi UI/role.
- CV Fit & Proper dan sumber impor disimpan privat serta diperiksa otorisasinya. Foto Successor memakai disk publik sesuai desain yang ada; jangan menganggap semua upload privat.
- PhpSpreadsheet tetap menyimpan workbook hasil ekspor dalam memori. Chunking model mengurangi materialisasi data awal, bukan mengubah workbook menjadi ekspor streaming tanpa batas.
- Cascading antarjenis placeholder pada template DOCX merupakan perilaku lama yang belum diubah; kasus loop token yang sama telah diperbaiki.
- Input manual Successor View dipertahankan. Tidak ada perubahan migration, reset database aplikasi, atau pengubahan seeder.

## Penerapan dan rollback

Perubahan belum diterapkan ke produksi. Tidak diperlukan migration untuk perubahan ini.

1. Tinjau diff dan gunakan lockfile yang disertakan; pasang dependensi dengan `composer install` sesuai prosedur deployment.
2. Pastikan `APP_URL` menunjuk URL HTTPS resmi, termasuk subdirektori bila ada; gunakan `APP_ENV=production`, `APP_DEBUG=false`, cookie Secure pada HTTPS, dan document root `public`. Tinjau akun hasil seeder demo sebelum penerapan; seeder tidak diubah oleh audit ini.
3. Jalankan production build dan proses cache/restart worker sesuai prosedur aplikasi. Uji login/reset, edit/impor pegawai, cetak mutasi, dan interaksi Fit & Proper dengan akun uji.
4. Rollback dengan menerapkan revisi aplikasi dan `composer.lock` sebelumnya, menjalankan `composer install`, membangun aset kembali, serta membangun ulang cache/restart worker. Tidak ada rollback skema/data yang diperlukan. Rollback juga membuka kembali masalah keamanan yang diperbaiki.
